Executive decision

Use one SDK core, but certify every supported wallet host explicitly

Keep

Existing architecture

The SDK already has meaningful ports for wallet signing, session signing, secure persistence, crypto, clock, fetch and telemetry. The package is secretless and keeps private wallet material outside its boundary.

Resolve first

Trust and conformance gaps

Challenge semantics, response correlation, stored-session validation and real-API conformance need evidence in every host. Ordinary web wallets also require a working CORS contract; mobile runtimes require executed adapter conformance.

Then proceed

Host conformance

After the shared gates pass, certify an HTTPS web wallet/PWA, the Chrome extension and native mobile applications against the exact package. Browser, MWA, Seed Vault, RPC and secure-storage adapters stay outside the SDK core.

This is not an adoption gate.

Whether users switch from Phantom or Solflare is a product experiment. This plan defines technical evidence required to avoid shipping broken account, payment, signing or recovery behavior while that experiment runs.

User-test-driven scope

The complete journeys the SDK must support

1. Wallet account and Ember signup

  1. The user selects the protected wallet address in an HTTPS web wallet, browser extension or native mobile wallet.
  2. The host creates a separate ephemeral Ed25519 session signer.
  3. The SDK requests a one-use Ember challenge for the selected wallet, integration, scopes and client binding.
  4. The SDK validates every challenge field before protected-wallet signing is requested.
  5. The host explains that the signature proves wallet ownership and cannot move funds.
  6. The host's protected-wallet signer signs the exact verified bytes.
  7. The SDK redeems the challenge and correlates the returned session to the requested authority.
  8. The host stores the refresh credential and ephemeral signer in approved secure storage.
  9. The user now has an Ember wallet subject and session, but has not paid and is not yet covered.
  10. Relaunch, rotation, expiry, revocation and account mismatch produce explicit recoverable states.

2. Pay once to activate cover

  1. The SDK returns offers for the active environment and cluster only.
  2. The host displays the exact price, benefit limits, duration, exclusions, terms and policy identifiers.
  3. The user explicitly accepts the displayed terms.
  4. The SDK records and verifies the terms receipt.
  5. The SDK creates a signed quote and verifies its authority, hash, signature, key state, product facts and expiry.
  6. The host constructs one exact USDC transfer using the verified mint, token program, amount, decimals, treasury account and reference.
  7. The host simulates and displays the transaction before protected-wallet approval.
  8. The signed payment state is persisted before broadcast so a crash cannot cause a second payment.
  9. The SDK submits the quote ID and transaction signature idempotently.
  10. The host polls the same payment ID until rejected or activated.
  11. Only a server-confirmed coverage instance means the selected address is covered.

3. Review and sign a dapp request

  1. The host verifies the requesting native app or web origin.
  2. The host decodes and simulates the exact unsigned transaction bytes.
  3. The SDK obtains a decision bound to the wallet, coverage instance, kind and exact bytes.
  4. The host displays covered, not covered, unsupported or unavailable honestly.
  5. A covered decision must have enough validity remaining before protected signing begins.
  6. The bytes are checked again immediately before signing.
  7. The host requests the protected signature from its wallet-signing adapter.
  8. The decision is checked again after protected signing returns.
  9. Fresh covered evidence is queued durably before signed bytes are released.
  10. If a covered decision expires, the host rechecks it. If cover is not offered, or remains unavailable after retry, the host may continue only after explicit user acknowledgement and must represent the result as uncovered.
  11. Confirmation and evidence lineage remain visible after the dapp receives the result.

4. Claim and evidence recovery

  1. The SDK checks eligibility for the exact covered decision.
  2. The user submits the appropriate direct-loss or delegate-drain claim.
  3. A stable idempotency key is reused after process or network interruption.
  4. The SDK correlates the returned claim to the decision, coverage instance and protected wallet.
  5. The host presents requested evidence and retention information.
  6. The SDK validates the short-lived upload grant before the host uploads bytes.
  7. The host uploads only the declared bytes and SHA-256.
  8. The SDK completes the same claim, evidence and request identifiers.
  9. Claim state is recovered from Ember rather than inferred from local UI state.
  10. An appeal creates a new review path without rewriting the original decision.

ADR-001 · One decision owner per signing use case

Status: Accepted 16 September 2026. The first live conformance attempt used Ember as the runner's external Wallet Standard signer. That composed two applications which each believed they owned session and cover-decision orchestration, producing contradictory wallet-level and request-level cover presentation. The run was stopped before either transaction was signed or broadcast.

Decision: the SDK remains a host-neutral protocol library. Its API conformance runner is a separate test application that owns its own lifecycle and uses a dedicated neutral external QA signer. Ember is rejected as that signer. Chrome and Android are product applications: each owns its complete cover decision, explicit approval, protected signing, broadcast and evidence flow while consuming the SDK only through its protocol boundary.

Rejected design: no privileged conformance bypass, trusted-dapp flag or externally injected cover decision will be added. Such a path would let an initiating application avoid the wallet's product decision and would create ambiguous authority at the security boundary.

Failure policy boundary: reviewForSigning() converts transport and validation failures into a typed unavailable result so callers do not receive a false coverage claim. The SDK cannot release a signature; the host owns that choice. Ember Chrome and Android may allow an uncovered signature only after explicit user acknowledgement, while a fresh covered decision is required for any protected claim and post-sign evidence.

Detailed gap register

Issues to resolve before certifying supported wallet hosts

P0 · Resolved
SDK-001

Validate the complete wallet challenge before protected signing

openSession() validates JSON shape, then sends challenge.message to the wallet signer without verifying its meaning. The API message correctly binds wallet, integration/version, environment, chain, ephemeral key, client binding, scopes, nonce, request ID and expiry. The SDK must parse and compare those facts before any host wallet signer sees a signature request.

Failure impact: an unexpected API response could become an arbitrary protected-wallet message-signing request.

Exit: field-by-field tampering tests prove the signer is never called for an invalid challenge in web, extension or native configurations.

The SDK-owned runner now installs the packed artifact, uses real Ed25519 session signers, requires an external wallet/Solana fixture, reconstructs durable state, exercises the full public lifecycle and emits a provenance-bearing report. The actual designated sandbox run is not yet recorded.

Failure impact: schema generation, mocked tests and a locally valid harness can pass while the deployed product journey fails.

Exit: run npm run conformance:api with the approved sandbox authority and wallet fixture; review and attach the passing report without importing backend or wallet source.

Prove native-mobile runtime compatibility

The clean fixture now installs the packed artifact, creates a React Native Android bundle with Metro, compiles it with Hermes 250829098.0.14, rejects Node-only imports, matches the request-proof vector and restores serialized authority in a second process without a duplicate challenge. SDK-004

Correlate every successful response with its request and active authority

Most methods trust any response that matches the generated schema. Explicit checks are needed for offer ID, terms facts, quote ID, payment signature, payment ID, coverage ID, wallet subject, protected wallet, decision kind, decision ID, claim ID and evidence identifiers.

Failure impact: a validly shaped but misrouted or stale response can be accepted as the result of another operation.

P1 · Resolved
SDK-005

Treat persisted sessions as untrusted input

requireSession() checks signer, integration, environment and access expiry, but the session store result bypasses the generated runtime schema. Malformed timestamps, scopes and identifiers can enter through restored storage.

Failure impact: corrupted or old app data produces inconsistent recovery behavior across hosts.

Exit: one shared parser rejects and clears malformed persisted sessions, while valid sessions survive process restart.

P1 · Resolved
SDK-006

Stop telemetry from receiving resource identifiers

The telemetry emitter passes the concrete request path even though the README promises a path template. Dynamic paths can reveal payment, coverage, decision, claim and evidence identifiers.

Failure impact: integrations can accidentally export customer-linked identifiers to analytics systems.

Exit: telemetry emits an operation and static route template only; a privacy test rejects dynamic identifiers.

SDK-007

Close important public state types

Coverage status, upload status and method, quote-key state, commission kind, quote cluster and parts of claim decisions remain unrestricted strings even where the backend has a closed state model.

Failure impact: hosts add string comparisons, default incorrectly or silently diverge.

Exit: backend OpenAPI exposes deliberate enums or an explicit forward-compatible unknown-state contract, and generated SDK schemas enforce it.

P1 · Resolved
SDK-008

Complete lifecycle method tests

Every public client method now executes in the behavior suite. Domain tests cover session, offers, terms, quotes, payment, coverage, decisions, post-sign evidence, claims, appeals and evidence uploads.

Failure impact: public methods could otherwise regress without failing package CI.

Exit: success behavior, response correlation, retry/non-retry policy, idempotency, cancellation, malformed responses and fail-open signing are enforced by the SDK gate.

P1 · Resolved
SDK-009

Resolve source-of-truth drift risk

The audit found two non-authoritative SDK source mirrors plus multiple working checkouts. Package source authority and imported-contract provenance were not machine-enforced.

Failure impact: wallet consumers can certify or copy different implementations.

Exit: this repository declares sole package authority, checks the imported contract revision and digest, publishes that provenance, and documents all external copies as consumers or temporary mirrors rather than synchronization peers.

P1 · Resolved
SDK-010

Validate evidence-upload grants before host use

Upload method, URL and status are broad strings. A production host should not blindly send claim material to an unexpected scheme, method or destination.

Failure impact: sensitive evidence could be sent using an unsafe or unsupported grant.

Exit: production grants require HTTPS, the contract-defined method, valid expiry and a documented header policy before returning to the host.

P1
SDK-011

Make session renewal behavior explicit

The backend defines a 15-minute access session and a 24-hour refresh window, but rotation requires proof from the still-active current session. A suspended app, sleeping extension worker or inactive browser tab that resumes after 15 minutes must ask for wallet ownership again; the 24-hour token is useful only for proactive rotation.

Failure impact: hosts can appear to promise silent 24-hour recovery that the protocol intentionally does not allow.

Exit: SDK documentation and conformance tests distinguish active, rotate-soon, expired/re-authentication-required and refresh-window-expired states across all supported hosts.

P1 · Resolved
SDK-012

Restore a clean release audit

Supported code-generation and test tooling now resolves with safe transitive versions. The full npm audit reports zero vulnerabilities without suppressing findings.

Failure impact: the next release can be blocked or the gate can be bypassed under schedule pressure.

Exit: supported tool versions pass full audit and the complete release workflow without suppressing unrelated findings.

P2
SDK-013

Document quote-key trust and compatibility policy

Quote verification fetches public keys from the same configured API and allows active or retired keys. The package also hardcodes acceptance of the current Core Annual production facts and the specific devnet QA offer.

Failure impact: operators may describe verification as fully offline, or product changes may unexpectedly require an SDK release.

Exit: document key freshness/cache behavior, revocation expectations and which product-contract changes require a new SDK version.

SDK-016

Define browser session ownership and concurrency

The host policy partitions by environment, integration ID/version and wallet address. Session transitions take a partitioned Web Lock and re-read storage after ownership is acquired; concurrent-tab conformance proves only one authority is opened.

Failure impact: two host instances can race rotation, restore the wrong wallet's session or clear authority owned by another active instance.

Exit: the policy and fixture keep browser coordination outside the SDK core while enforcing the shared session invariants.

Package metadata and documentation now name HTTPS web, Chrome extension and native wallets. The library uses an explicit neutral ES2022 build, while the packed artifact is browser-bundled and executed without Node-only dependencies.

Failure impact: partners cannot distinguish an intended supported host from an incidental successful bundle, and a future dependency change can break browser consumers without CI noticing.

Exit: the declared compatibility policy, package metadata and CI browser gate now enforce the supported host claim.

Critical cross-host rule

Decision expiry during protected-wallet approval

The backend rule already exists.

A cover decision lasts 60 seconds. Post-sign evidence received at or after expiry is rejected with decision_expired. This is one shared rule for web, extension and native hosts.

Failure matrix

  • Offline before request.
  • Connection loss after server commit.
  • Timeout with late response.
  • Caller cancellation.
  • Process death after signing.
  • Malformed success payload.
  • Wrong resource response.
  • Expired authority.

Security matrix

  • Challenge tampering and replay.
  • Session signer mismatch.
  • Wrong client binding.
  • Wrong environment or cluster.
  • JTI replay.
  • Body/path mutation.
  • Quote hash/signature/key failure.
  • Telemetry identifier leakage.

Manual checkpoints

Minimum end-to-end scripts before a host is declared supported

Account script

  1. Select wallet.
  2. Inspect challenge.
  3. Approve ownership.
  4. Verify backend subject.
  5. Restart and restore.
  6. Rotate near expiry.
  7. Revoke and confirm failure.

Payment script

  1. Read offer.
  2. Accept exact terms.
  3. Verify quote.
  4. Simulate USDC payment.
  5. Sign once.
  6. Interrupt after broadcast.
  7. Resume same payment.
  8. Verify one coverage instance.

Signing script

  1. Request covered review.
  2. Inspect exact bytes.
  3. Approve protected signing.
  4. Queue evidence.
  5. Confirm lineage.
  6. Repeat near expiry.
  7. Expire during approval.
  8. Confirm no silent cover claim.

Claim script

  1. Check eligibility.
  2. Create with stable key.
  3. Interrupt response.
  4. Retry without duplicate.
  5. Request upload.
  6. Validate grant.
  7. Complete evidence.
  8. Read authoritative state.

Privacy script

  1. Enable telemetry collector.
  2. Exercise all dynamic routes.
  3. Inspect events.
  4. Confirm no IDs, wallets, signatures, bodies or tokens appear.

Package and host script

  1. Download the exact release.
  2. Verify integrity and provenance.
  3. Install without workspace links.
  4. Run ESM/CJS packaging, HTTPS web, Chrome extension and declared mobile checks.
  5. Confirm the bundle secret scan.
